# ScoreKeep Functional Specification — 13 Security, Privacy, and Data Protection

## 1. Overview

Security, privacy, and data protection in ScoreKeep exist to preserve user trust in baseball records throughout team preparation, live scoring, review, reporting, importing, exporting, purchasing, support, and long-term use. The application may contain team information, player information, player photos, team logos, game records, scoring history, imported files, exported files, purchase-related state, and user preferences.

ScoreKeep must protect these records from accidental loss, unintended disclosure, unauthorized changes within the app workflow, and misleading reuse. Protection is not limited to private information; it also includes preserving the integrity of baseball facts such as scores, at-bats, lineups, pitcher records, substitutions, and historical reports.

The user experience should make privacy and data-protection behavior understandable to non-technical users. Users should know when they are creating records, changing records, importing outside content, sharing files, deleting information, opening external services, or using purchase-related capabilities.

## 2. Security and Privacy Principles

Users retain ownership of the baseball records they create, import, correct, and export. Teams, players, rosters, games, scorekeeping events, photos, logos, reports, and preferences should remain treated as user-owned product data rather than as purchase-system data.

Local baseball records should remain available without unnecessary network dependence. Network features may support roster downloads, remote announcements, purchase checks, external links, and support, but they must not become a hidden requirement for ordinary access to local scoring records.

ScoreKeep should collect, request, display, import, export, or transmit information only when required for a visible feature or an established app behavior the user can understand. Optional media, optional notes, optional location information, optional coach details, and optional player details should remain optional unless a specific workflow genuinely needs them.

Sharing should occur through deliberate user action. A roster, game file, report, PDF, player photo, team logo, or other generated output should not leave the app merely because it exists locally.

Imported data is treated as untrusted until reviewed. Compatible-looking files, downloaded rosters, deep-link inputs, and shared files may contain outdated, malformed, duplicate, ambiguous, or personal information and should not be allowed to silently alter unrelated records.

Purchase state remains separate from baseball records. Premium access may control access to selected capabilities, but it must not determine ownership of teams, players, games, lineups, scoring events, reports already generated by the user, photos, logos, or compatible exported source data.

Sensitive user data should not be exposed through error messages or support requests unnecessarily. Messages should identify the affected record or action without exposing unrelated records, account details, photos, rosters, or game files.

Security protections must not lock users out of their own compatible records. Validation, permission handling, purchase checks, and compatibility warnings should protect records from unsafe changes while still preserving clear access to user-owned data.

## 3. User Data Ownership

Users own the teams, players, rosters, games, lineups, scoring events, pitcher records, substitutions, reports, photos, logos, imported files, exported files, and preferences they create or manage through ScoreKeep. The app should preserve that ownership across ordinary launches, offline use, purchase-status changes, app updates, supported imports, and supported exports.

Existing records remain accessible after premium expiration. Premium status may affect creation limits, report generation, downloads, or other gated features, but it must not turn existing baseball records into inaccessible purchase-owned content.

Users can correct and export supported records. Corrections should be deliberate and scoped to the selected team, player, game, lineup, scoring event, pitcher record, substitution, report source, photo, logo, or preference. Export of compatible user-owned source data should not be blocked solely because premium access expired.

Purchase state does not determine baseball ownership. Account changes, restore uncertainty, price-loading failures, or purchase cancellation must not delete teams, players, games, scoring history, photos, logos, or preferences.

App updates should not silently make existing data inaccessible. If a supported migration, compatibility change, or product limitation affects access to existing records, the app should communicate the change honestly and preserve the safest available path for review, correction, export, or support.

Deleting the app may affect locally kept records unless the user has separately backed them up, exported them, or restored them through a supported system backup. ScoreKeep should communicate backup and export expectations honestly and must not imply guaranteed recovery when the product cannot guarantee it.

## 4. Local Data Expectations

Local ScoreKeep records should remain available offline for core workflows, including team management, player management, game setup, live scoring, corrections, local reports where available, local imports, local exports, and review of saved records.

Records should persist across ordinary app launches and device restarts. A user who leaves during team editing, lineup preparation, scoring, reporting, or import review should return to the latest coherent state that can be presented honestly.

Preference resets must not delete baseball data. Resetting sort choices, dismissed messages, paste settings, or similar preferences should not remove teams, players, games, at-bats, lineups, pitcher records, substitutions, photos, logos, imports, exports, or reports.

Purchase expiration must not delete local baseball data. Failed purchase checks, expired access, account changes, or restore uncertainty must leave existing records intact and accessible.

Failed operations should preserve the prior usable state. A failed import should leave local records unchanged. A failed export should leave the source data unchanged. A failed report should not alter the source game. A failed purchase action should not consume allowances or change baseball records.

App reinstall, device replacement, and Apple account changes require clear communication. ScoreKeep should distinguish records currently present on the device, records restored from a system backup, records reopened from exported files, and records not recoverable through the app.

Application updates must not silently delete local records. If an update encounters incompatible or damaged records, the user should receive a clear explanation and a safe recovery path where practical.

## 5. Data Minimization

ScoreKeep should use only the information needed for its visible features. Required baseball identity should be limited to what the selected workflow needs, while optional fields remain optional unless a specific workflow requires them.

Coach information, player photos, team logos, notes, location, pitcher information, and similar details may improve a roster, game, report, or scorecard, but they should not be required for unrelated workflows. A user should be able to create useful teams, players, games, scoring records, and reports without adding optional personal details or media.

Remote announcements should use only the information needed to present supported product notices. Purchase checks should use only the information needed to determine visible purchase status. Roster downloads should use only the information needed to retrieve and review the selected roster source. Support information should be limited to what is needed to understand the user's request.

Optional fields should not become hidden prerequisites. If a workflow requires a field that is normally optional, the requirement should be visible at the point of use and explained in product language.

## 6. Player and Team Information

Player names, jersey numbers, positions, batting information, team membership, coach information, team notes, game participation, and historical records may identify real people and real teams. ScoreKeep should treat this information as meaningful user data even when it is not secret.

Users may use ScoreKeep for youth, school, recreational, amateur, family, or informal teams. The app should encourage responsible sharing by clearly identifying what roster, player, team, game, report, photo, logo, or exported file is about to be shared.

Team and player information should not be exposed through unrelated errors, purchase workflows, support requests, announcements, or external links. When a record must be named to explain an action, the app should identify only the affected record or scope.

Historical participation should remain understandable. Changing a player's current team, number, position, photo, batting information, or active roster status should not silently rewrite the meaning of past games and reports.

## 7. Photos and Logos

Player photos and team logos are optional media. They may represent minors, school teams, amateur teams, family members, or local organizations and should be treated with care throughout selection, import, download, display, report generation, sharing, replacement, and removal.

Images selected locally should remain under user control. Images received through imports or downloads should be reviewed before they replace existing local media. If an imported player photo or team logo is missing, unreadable, unexpected, or attached to an ambiguous record, the user should be able to skip it, keep the current image, or cancel the import where practical.

Images must never be uploaded or shared merely because they are stored locally. Sharing or including images in exported files, PDFs, reports, or other generated output should occur only through a visible feature initiated by the user.

Removing a player photo should not delete the player. Removing a team logo should not delete the team. Replacing media should affect only the intended player or team and should not change unrelated records.

Historical reports may continue to include media that was present when the report was generated or shared. Removing local media later does not recall files, PDFs, printouts, screenshots, or other output already shared outside ScoreKeep.

## 8. Game and Scoring Records

Scores, at-bats, runs, hits, errors, outs, RBIs, stolen bases, pitcher records, lineups, substitutions, notes, game location, and historical reports are authoritative baseball data within the product. Security and privacy behavior must protect both confidentiality and factual integrity.

Licensing state never changes game facts. Expired premium access, restore uncertainty, account changes, or failed purchase checks must not alter scores, scoring events, lineups, pitcher records, substitutions, notes, locations, or historical reports.

Reports and PDFs are generated outputs derived from source records. They should not become the authoritative source record, and a generated output should not silently rewrite the underlying game.

Corrections should be deliberate. Editing a score, at-bat, inning, out, RBI, stolen base, pitcher record, lineup, substitution, note, or location should be scoped to the selected game and should make downstream effects understandable.

Historical records should not be silently rewritten by current roster changes. Renaming a player, removing a player from active roster use, changing a jersey number, or replacing a photo should not make past games misleading.

Sharing game files requires user action. A game file, report, PDF, or historical record should not be sent, saved outside the app, or opened in another destination without a visible user-initiated sharing, export, or open action.

## 9. Import Security and Privacy

Imported files are untrusted until validated and reviewed. This includes local files, shared files, downloaded rosters, seeded records, deep-link requests, and website-hosted compatibility files.

No automatic permanent changes should occur before review. Import review should identify the file type, apparent record scope, teams, players, games, photos, logos, duplicates, unresolved names, skipped records, and conflicts where practical.

Malformed files cannot damage unrelated local records. Wrong file types, corrupted content, unsupported future content, incomplete records, ambiguous player matches, impossible scoring data, and unsafe media should be rejected, skipped, or held for user review before local data changes.

Imported photos and logos require review before replacing local media. Unknown teams and players should remain visibly unresolved rather than silently mapped to unrelated local records.

Duplicate detection must not expose or merge unrelated records. Similar names, reused jersey numbers, changed photos, changed teams, or matching dates should lead to comparison and choice when ambiguity matters.

Imported files may contain personal information. Import summaries should explain what changed, what was skipped, what remains unresolved, and whether photos or logos were included. Canceling import leaves local data unchanged.

## 10. Export and Sharing Privacy

Exporting or sharing team rosters, player information, player photos, team logos, games, reports, PDFs, and historical records requires deliberate user action. The user should understand what record, team, game, report, roster, or file is being shared before the operation completes.

The app should make inclusion of photos or logos understandable where practical, especially when exporting player rosters, team records, PDFs, or reports that may be sent outside the user's device.

Canceling sharing leaves local data unchanged. If the user cancels a share sheet, save panel, file destination, print action, or external handoff, the source team, player, game, report, photo, logo, and preferences remain unchanged.

Shared files are outside ScoreKeep's control after the user sends, saves, prints, exports, or opens them in another destination. ScoreKeep must not represent previously shared files as recalled or deleted when only local records changed.

Export must not include unrelated teams, players, games, photos, logos, hidden records, or historical records outside the selected scope. Premium expiration must not block export of compatible user-owned source data.

## 11. Website, Downloads, and Remote Content

Network access should occur only for visible supported features or established app behavior such as MLB roster downloads, roster manifest access, remote announcements, external privacy-policy links, external license links, support links, deep links, and website-hosted compatibility files.

Remote failure must not block local scoring. If downloads, announcements, external pages, purchase services, or remote files are unavailable, the user should still be able to create, edit, score, correct, review, import local files, export local files, and view local records where the feature does not require the failed remote service.

Downloaded content is reviewed before changing local data. A downloaded roster or compatibility file should be treated like any other import: visible, validated, scoped, and confirmed before it becomes permanent.

Announcements do not change baseball data. Remote announcements may inform the user, but they should not create, edit, delete, merge, export, or share teams, players, games, scoring records, photos, logos, or preferences beyond announcement-related dismissal state.

Deep links do not bypass validation or confirmation. A link may open a supported destination or prefill a supported workflow, but it must not silently import, overwrite, share, delete, purchase, or alter baseball records.

The app should not depend on unrelated website tracking or human-facing HTML for data compatibility. Compatibility files should remain understandable as supported ScoreKeep files rather than as hidden byproducts of a web page.

## 12. Purchase and Account Privacy

Purchase status, season access, price loading, status checking, Apple account context, free allowances, restore uncertainty, and purchase support are separate from baseball records.

Purchase state may affect feature availability, but it must not delete, rewrite, hide, or claim ownership of teams, players, games, lineups, scoring events, pitcher records, substitutions, photos, logos, preferences, imported files, exported files, or compatible user-owned source data.

Users should not be asked to expose unnecessary purchase details. Purchase support should avoid collecting more information than needed to understand the problem, and support instructions should not request passwords, account credentials, unrelated account information, or unrelated personal data.

Status uncertainty should be communicated honestly. If product details, price, restore state, current entitlement, Apple account context, or service availability cannot be confirmed, the user should know what is uncertain and what local work remains available.

Failed or canceled purchases do not consume allowances. Account changes do not delete local baseball records. Purchase recovery and baseball-data recovery are separate concerns and should be described separately.

## 13. Permissions

Permission requests involving photos, files, external links, sharing destinations, purchase services, and other device capabilities should occur in context. The user should understand why access is requested and which workflow is affected.

Permission denial must not block unrelated features. A user who denies photo access should still be able to manage teams, enter players, score games, use reports without optional media where supported, and continue unrelated local workflows. A user who denies file access should be able to continue with local records and choose another supported path where practical.

Optional permissions remain optional. ScoreKeep should offer a safe alternative where practical, such as continuing without a photo, choosing another file, canceling import, returning to the roster, or sharing a report without optional media.

Permission denial never deletes prior records. Teams, players, games, photos already attached, logos already attached, scoring records, preferences, and purchase-related state should remain intact when the user declines or later revokes access.

## 14. Help, Support, and Diagnostic Information

Support behavior should be privacy conscious. The user chooses what information to share, and ScoreKeep should not require baseball records, photos, rosters, game files, or exported reports unless they are genuinely needed and voluntarily provided.

App version, device context, purchase-status category, visible error summary, selected workflow, and file type may be useful for support. Such information should identify its scope and should not include unrelated teams, players, photos, logos, game details, account credentials, passwords, or personal information.

Error summaries should be human-readable. A user should understand which team, player, game, import, export, purchase action, permission, or report was affected and whether local data changed.

Support instructions should avoid asking users to expose passwords, account credentials, unrelated personal information, or complete baseball records when a smaller description is enough. Shared diagnostic material should identify whether it includes roster data, game data, media, purchase context, or only a summary.

## 15. Deletion and Removal

Deleting or removing teams, players, games, photos, logos, imported records, sample data, preferences, announcements, and generated output stored inside the app requires explicit intent. Destructive actions should identify the record, explain meaningful historical dependencies, and provide cancellation before changes occur.

Removing a player from active roster use differs from deleting historical identity. A player who appears in past games, lineups, substitutions, pitcher records, reports, or scoring events should not be removed in a way that leaves history misleading without a clear warning.

Removing media does not delete the team or player. Removing a photo affects only the intended player. Removing a logo affects only the intended team. Replacing media should not affect unrelated teams, players, reports, or historical source records.

Preference reset does not delete baseball data. Dismissing or clearing announcements does not delete baseball data. Removing sample data should identify the sample records involved and should not remove unrelated user-created records.

Deleting local records does not recall previously shared files, saved exports, printed reports, PDFs, screenshots, or files opened in other destinations. Canceling deletion leaves data unchanged.

## 16. Backup, Transfer, and Device Changes

Users should be able to export supported backups or compatible files and transfer them between devices through supported sharing and file-opening workflows. Opening previously exported files should require the same validation, review, and confirmation as any other import.

Reinstalling the app, replacing a device, restoring from a system backup, or moving to another Apple account may affect which local records are available. ScoreKeep should describe what is currently present, what can be imported from exported files, and what cannot be guaranteed.

Purchase recovery and baseball-data recovery are separate concerns. Restoring premium access should not be presented as restoring teams, players, games, photos, logos, reports, or exported files. Recovering baseball records should not depend on purchase status except where a specific gated feature is needed after the records are present.

ScoreKeep must not promise automatic recovery that the product cannot guarantee. Backup, export, and transfer messages should be honest about user action, system backup behavior where applicable, and the limits of locally held data.

## 17. Data Retention Expectations

Local teams, players, games, historical records, photos, logos, preferences, announcement dismissals, sample-data state, and purchase-related state remain until the user deletes them, the system removes the app's local data, or a supported migration changes them.

Expired premium status does not delete baseball data. Archived records remain user-accessible. A user should be able to review and export compatible owned source records even when premium access is not currently active.

Temporary previews, draft imports, canceled imports, canceled shares, rejected files, and abandoned conflict reviews should not become permanent records. If any partial result remains visible, the app should identify it clearly and provide a safe way to remove or complete it.

Generated files saved outside the app follow the destination's retention rules. Removing local records in ScoreKeep does not remove reports, PDFs, roster files, game files, printouts, screenshots, or shared copies that already left the app.

## 18. Privacy in Reports and Generated Output

Scorecards, batting reports, pitching reports, PDFs, printed reports, shared reports, historical reports, and other generated output may contain personal or team information. They may include player names, jersey numbers, positions, batting results, pitching results, game locations, notes, player photos, team logos, scores, and historical participation.

Users should understand the report scope before sharing. The app should identify the selected team, player set, game, date, report type, and relevant media inclusion where practical.

Reports do not become the authoritative source record. They represent generated output from saved baseball data at a point in time. Removing local data does not remove previously shared, printed, saved, or exported reports.

Generated output should not accidentally include unrelated hidden records, unrelated teams, unrelated players, unrelated games, or media outside the selected scope. Reports should remain understandable without optional photos or logos.

## 19. Validation Requirements

ScoreKeep must validate privacy and data-protection risks before completing actions that could share, overwrite, delete, merge, or misrepresent records.

Sharing validation should prevent the wrong team, wrong roster, wrong game, wrong report, or wrong export scope from being shared without clear user-visible identification. Export scope must exclude unrelated records.

Media validation should prevent a photo from being attached to the wrong player and a logo from being attached to the wrong team. Replacement should show the intended target and preserve the prior record if the user cancels or the operation fails.

Import validation should detect imported personal data that lacks a clear target, unknown teams, unknown players, ambiguous duplicates, unsafe media replacement, malformed files, unsupported content, and deep-link attempts to bypass confirmation.

Permission validation should prevent permission prompts from appearing without context. Denial should return the user to a safe state and explain which optional feature is unavailable.

Deletion validation should prevent deleted records from still appearing active. If historical dependencies exist, the app should explain them before deletion and preserve the record if the user cancels.

Preference validation should prevent reset actions from appearing to delete baseball data. Purchase validation should prevent premium expiration from appearing to remove owned records. Support validation should prevent flows that request excessive information. Device-change messaging should not imply guaranteed recovery when recovery has not occurred.

Report validation should identify when reports include personal information, photos, logos, notes, locations, or historical details that the user might not expect. Safe recovery behavior should be user-visible: cancel, return, choose another record, continue without optional media, skip unsafe import content, keep current values, export a narrower scope, or contact support with a scoped summary.

## 20. Data Integrity Requirements

Security and privacy behavior never changes baseball facts by itself. User-owned records remain accessible regardless of premium status. Permission denial never deletes data. Imported data never becomes permanent before confirmation.

Export includes only the selected scope. Media replacement affects only the intended record. Preference reset never deletes baseball records. Purchase state remains separate from scoring records. Support workflows do not alter local data.

Failed network actions leave local data unchanged. Deletion affects only confirmed records. Previously shared output is not falsely represented as recalled or deleted. Device changes do not invent recovery that did not occur.

Privacy failures must never silently merge teams, players, games, rosters, photos, logos, pitcher records, substitutions, scoring events, reports, or preferences. When ambiguity exists, the app should preserve the prior state and require a user-visible choice.

## 21. Accessibility Requirements

Privacy and security interactions must remain accessible to users relying on accessibility features. Permission explanations should be readable by VoiceOver and should clearly identify the affected feature.

Sharing screens should clearly identify what will be shared, including the selected team, game, roster, report, photos, logos, notes, and location where practical. Deletion confirmations should identify the record and the consequence without relying only on color, layout, or transient messages.

Import conflict review should support VoiceOver, larger text, high contrast, color-independent warnings, and clear navigation between conflicts. Users should be able to understand unresolved teams, unresolved players, duplicate records, media replacement choices, skipped content, and cancellation results.

Photo and logo removal should be accessible and should identify the target player or team. Critical privacy messages should remain available long enough to read and should not disappear before assistive technology can announce them.

The interface should clearly distinguish local records from shared output, imported previews from confirmed records, and purchase status from baseball data ownership.

## 22. Exceptional Situations

If a user shares the wrong roster or a file containing player photos, ScoreKeep cannot recall the file after it leaves the app. The app should make the selected record and media scope clear before sharing and should let the user cancel before completion.

If a user deletes a player used in historical games, the app should explain the historical dependency and distinguish removing active roster use from deleting historical identity. Canceling should leave the player and history unchanged.

If a user removes a team logo, the team and games remain. Future views and reports should continue without the logo where supported, while already shared output remains outside ScoreKeep's control.

If an imported file contains unexpected personal data, the app should present the scope, unresolved targets, media, and conflicts before applying changes. The user should be able to cancel, skip unsafe content, or import only understandable records.

If the app is offline, local scoring, local review, local editing, and local files should remain available where they do not require a remote service. Roster downloads, announcements, external links, and purchase checks may be unavailable without changing local baseball data.

If the roster-download service fails, the user should receive a clear failure message and local records should remain unchanged. If the user denies photo or file permission, the app should explain the affected optional workflow and preserve prior records.

If the user reinstalls the app, changes devices, changes Apple accounts, or loses a previously exported file, ScoreKeep should avoid promising recovery that has not occurred. The app should distinguish purchase recognition from baseball-record recovery and should support opening compatible exported files when available.

If the user asks support for help with a damaged game file, support guidance should request only the information needed and should make voluntary file sharing clear. If a previously shared PDF contains outdated information, the app should explain that local corrections do not change already shared or printed output.

If premium access expires while local data remains but purchase status cannot be verified, the app should preserve existing baseball records, communicate purchase uncertainty honestly, and keep purchase support separate from data ownership.
