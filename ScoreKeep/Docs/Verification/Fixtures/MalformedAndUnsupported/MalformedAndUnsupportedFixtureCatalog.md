# Malformed and Unsupported Compatibility Fixture Catalog

<!-- MARK: - 1. Purpose and Authority -->
## 1. Purpose and Authority

This catalog completes implementation-catalog task `0.11 Malformed and unsupported fixture curation` from `ScoreKeep/Docs/Design/29-ImplementationTaskCatalogAndDependencyMatrix.md`.

The fixture set is verification evidence for malformed, unsupported, ambiguous, corrupted, wrong-extension, forward-compatibility, and relationship-risk inputs. It changes no production behavior, file format, UTI declaration, import route, export route, validation rule, persistence behavior, project membership, seeded data, StoreKit configuration, or existing representative fixture.

Governing evidence inspected: Documents 21, 27, 28, and 29; `ScoreKeep/Docs/CompatibilityRouteInventory.md`; `ScoreKeep/Docs/Verification/Fixtures/ScoreKeep_Players/ScoreKeepPlayersFixtureCatalog.md`; `ScoreKeep/Docs/Verification/Fixtures/ScoreKeep_Games/ScoreKeepGamesFixtureCatalog.md`; existing roster and game fixtures; `ScoreKeep/Common/CommonData.swift`; `ScoreKeep/Sharing Data/ImportPlayersView.swift`; `ScoreKeep/Sharing Data/ImportService.swift`; `ScoreKeep/List Data/StartView.swift`; `ScoreKeep/List Data/StartPhoneView.swift`; `ScoreKeep/Info.plist`; and `ScoreKeep/Common/Extensions.swift`.

All fixture content is synthetic and inert. No real youth-player data, real user files, real photos or logos, web responses, external scripts, tracking code, credentials, purchase information, private URLs, executable payloads, or resource-exhaustion payloads are included.

## 4. Result Classification Legend

The fixture tables use compact result language so each fixture can record the required fields without pasting full contents.

Expected routing result:

| Code | Meaning |
| --- | --- |
| `candidate roster` | Current exact-extension routes should treat the file as roster-compatible input. |
| `candidate game` | Current exact-extension routes should treat the file as game-compatible input. |
| `routing rejection` | Current exact-extension routes should reject before decode on iPhone and share validation; iPad filename fallback may differ where noted. |
| `route mismatch` | Extension and content disagree; later classification should identify mismatch before writes. |

Expected JSON, decoding, semantic, review, and persistence results:

| Code | Meaning |
| --- | --- |
| `parse fail` | JSON syntax parsing should fail. |
| `valid JSON` | JSON syntax is valid. |
| `decode fail` | Current Codable decoding should fail. |
| `decode succeeds` | Current Codable decoding should succeed. |
| `semantic warning/reject` | Codable may succeed, but baseball or compatibility validation should warn or reject later. |
| `no review` | No reviewable roster or game record should be presented. |
| `review with warning` | Later review should be possible only with explicit warning or repair classification. |
| `no persistence` | No SwiftData write should occur. |
| `unsafe to execute` | Do not execute current production import application because repository evidence shows crash or unsafe partial-write risk. |

Production execution safety is listed separately. `No` means no current production importer application should be executed for that fixture without an isolated harness.

<!-- MARK: - 9. Decoder Versus Application Failure Decisions -->
## 9. Decoder Versus Application Failure Decisions

JSON parse failures: the two zero-byte files and the referenced truncated malformed files should fail before Codable decoding.

Codable decode failures: wrong roots, missing required non-optional keys, wrong value types, invalid UUID strings, null non-optional values, missing non-optional arrays, invalid base64 `Data`, and unrelated JSON under a valid extension.

Structural decode success but semantic invalidity: empty roster array, invalid date string, duplicate identifiers, conflicting team identity, broken child relationships, unsupported raw batting direction, negative score, unknown fields, and valid base64 non-image media.

Review-stage rejection or warning: every decode-success fixture with relationship, semantic, unknown-field, unsupported, empty, duplicate, or media interpretation risk should enter later review only with warnings or repair classification.

Relationship-resolution failure: broken at-bat, lineup, and pitcher fixtures are decode-success files that must not be applied through current production import. Current user-routed code contains force unwraps in at-bat and lineup import, and current service code rejects more-than-two-team evidence only after persistence-oriented processing begins.

Persistence-application failure: no fixture in this task should be imported into real SwiftData. Files that decode but cannot safely be applied are classified as requiring an isolated persistence harness before execution.

Routing rejection before decoding: `.json`, `.txt`, and exact-extension-rejected lowercase or double-extension cases should be verified at route level separately from decoder behavior. iPad and iPhone route behavior intentionally remains documented as divergent current evidence.

Unsafe or crash-prone behavior: broken game relationships and non-image media display were not executed against production import or image-rendering code.
